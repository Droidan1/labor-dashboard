Inventory, unbundled

Today Inventory is one page holding three tools as collapsed cards and a modal, while Bin Dump, Inventory Receiver, Mark Out of Stock and Opportunity Buys sit beside it as four separate top-level nav items. This preview turns Inventory into a sidebar group — the same mechanism Marketing and Merchandising already use — and promotes Add Item, Inventory Viewer and Schedule Sale to real pages, rebuilt on the V1 Operator panel from DESIGN.md §4.8.

Nothing here is wired. This file lives in docs/, which scripts/build.sh deliberately excludes from its copy allowlist, so it can never reach production. The numbers are plausible sample data. Every field, endpoint and validation rule shown is read from the live index.html and worker.js — nothing is invented.

2What each page gains

Beyond the V1 skin, these are the behaviour changes the redesign makes. Each one exists because the current page has a specific gap, named below.

A
Add Item — the L3 → L2 conflict moves before the submit
Today you pick the reporting group (L2) first, then type a Clover category (L3). If the L3 is a built-in that already maps elsewhere, the worker creates the item anyway and tells you afterwards, in a yellow banner, that sales will book somewhere other than where you chose. In the redesign the category comes first and the reporting group follows from it — auto-filled and explained when the mapping is known, free to set when the category is genuinely new. The conflict becomes impossible to submit by accident rather than something you read about afterwards.
B
Add Item — margin is shown while you type
Price and cost are both already collected and never multiplied together. A buyer entering $6.99 against a $2.40 cost currently gets no signal that this is a 65.7% margin until it shows up in a report weeks later.
C
Add Item — the six-store result becomes readable
The endpoint already returns a per-store results[] with a stage and a duplicate flag. The current UI renders it as a four-column table (Store / Status / Item ID / Category) with ✓ Created, ⚠ Exists, ✗ Error — and only when more than one store was targeted. The redesign gives each outcome a coloured row, the reason in plain English, and the one action that resolves it.
D
Inventory Viewer — GP% becomes a column, and “no cost” stops reading as free
Price and cost are both already in the table. A missing cost renders as —, never $0.00 or 0% — the same rule DESIGN.md §4.8 sets for the Coverage heatmap, where printing 0% for absent data tells you to cut a category nobody measured.
E
Inventory Viewer — an item in two Clover categories is finally visible
The endpoint returns categories[] as well as the flattened category, precisely because collapsing to the first one hid whether an item also sat in the sku book alongside a real category. The current table shows only the flattened name. A 2 cats badge surfaces it.
F
Schedule Sale — stops being a modal
It is currently a modal reachable only by ticking rows in the Inventory Viewer, and it is the one modal in the page driven by inline style.display rather than .hidden — with a special case in closeInvModal to match. As a page it is reachable directly, the item list and the schedule log sit on the same screen, and the special case goes away.
G
Schedule Sale — the 409 overlap becomes a designed state
The worker refuses a schedule that overlaps a pending or active one for the same item and returns a 409 naming the item. Since one POST goes out per checked store, a realistic outcome is “five scheduled, one refused” — which the current status line cannot express.
3One thing to decide, four things found

The mock above puts all seven pages inside the group. Your message listed four for the dropdown and then asked for the other three to get their own page — which could mean either. Say which and I will build it that way.

?
Do Add Item / Inventory Viewer / Schedule Sale go inside the Inventory group, or beside it?
Shown above: all seven inside the group, catalog tools first, floor tools after. The alternative is three top-level nav items plus a four-item Inventory group — but that puts nine Inventory-ish rows in a sidebar that already has Marketing and Merchandising groups, and “Add Item” as a top-level peer of “Dashboard” reads oddly. The order inside the group is trivial to change either way.
1
“Delete from all other stores” targets a closed store and misses a live one
confirmDelete() hardcodes ['BL1','BL2','BL4','BL8','BL12','BL14']. BL12 is Wyoming, which is closed; BL16 (Indy East) is missing — and every store dropdown on the page lists BL16 and not BL12. So today that checkbox silently leaves the item alive in Indy East. This is a live bug independent of the redesign; I would fix it in the same change unless you want it separately.
2
The whole mobile bar layout keys off the Inventory nav item
var isAdminBar = vis('nav-inventory') is the discriminator that decides whether a phone gets the flat admin bar or the manager bar with the centred Submit button. If nav-inventory becomes a group header, that check changes meaning. It needs re-pointing deliberately, and it is the single most breakable line in the change.
3
Moving the four pages into a group can blank an associate's whole app
applyAssociateNav hides every nav item, then un-hides only the granted ones. Bin Dump, Inventory Receiver, Mark Out of Stock and Opportunity Buys are exactly the four grantable pages. Un-hiding the child without also un-hiding the new group wrapper and sub-list leaves an associate with an empty sidebar.
4
The test that would catch a broken nav link does not run
scripts/test-nav-registry.mjs reports 17 passed, but its last block — the one asserting “every data-page has a matching page- section” — sits after process.exit(), and throws ReferenceError: REPO is not defined if reached. Verified by removing the exit and running it. That is precisely the check a nav restructure needs, so I would repair it first and let it guard the change.
5
Dead pagination, and four copies of the store list
updateInvPagination has no caller; invPagePrev / invPageNext are reachable only from buttons inside a container that is never shown, and step an offset loadInventory ignores. Separately, the six stores are hardcoded four times on this page — Add Item, the Viewer, the sale modal and the schedule log — which is how BL16 went missing from one of them.
