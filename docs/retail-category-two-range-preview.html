Categories — two date ranges instead of fixed buckets

Proposal: replace the Day / Week / Month / Quarter bucket control with two range pickers — one for the dates you want to look at, one for the dates you want them measured against. The buckets stay, as one-click presets that fill both. Everything below is live: change the ranges and the whole panel re-reads.

Why this is worth doing beyond flexibility. Two explicit ranges are answered by ?action=category-series, the per-day feed. That means the weekly-rollup path is not involved at all — so the 108-week wall disappears (quarter-vs-quarter works today, on the data that already exists), and "a month means two different things on one tab" stops being true, because there is only one feed left.

The panel

The preview uses native date inputs for custom ranges. The real one reuses the app's existing calendar popover (#wrs-range-cal-grids) and its preset list, so this control looks and behaves like the range picker already at the top of the page.

What this removes

Worth being explicit, because some of it is code shipped earlier today.

  • The week-derived path for this tab. Month and quarter are currently built from whole weeks assigned by end date; the Vs card is calendar-exact from day snapshots. Two ranges are always the second thing, so the caveat "these months are built from whole weeks" goes away — along with the discrepancy it was warning about.
  • The 108-week ask. Nothing requests weekly-t13&weeks=108 any more, so the short-history caption ("Only 42 of the 108 weeks … exist") has nothing to report.
  • The version guard ("the worker half of this deploy is older than this page") — same reason: it watches a feed this tab would no longer use.
To be clear about what stays. Both worker fixes remain load-bearing: the weeksWindow echo and the GROUP BY date(date,'weekday 6') correction serve the T13 tab, which reads weekly-t13 directly and was silently reading the wrong year's numbers. Only the two Categories-tab guards become dead code.

What it costs

category-series refuses beyond 840 store-days per request. Two ranges are two requests, each with its own budget, so the limit is per range:

RangeAll 7 storesOne store
Longest allowed120 days840 days
A quarter (~92 days)644 store-days ✅92 ✅
A year (365 days)2,555 ✗ refused365 ✅

So year-over-year is a single-store question on this path. The panel computes the store-days before asking and says so in the control, rather than letting the request come back 413 — try Last 12 Months with all stores below.

Questions I need answered before building

1. Do the bucket presets stay?
Built as shown: Day / Week / Month / Quarter survive as presets that fill both pickers, so one click still gets you "this month vs last month". The pickers are the truth; presets are shortcuts. Say if you would rather they go entirely.
2. Which comparison should B default to? (the one I would most like answered)
There are two sensible rules and they answer different questions. Try the Compare to control:
Rule"This Quarter" (Jul 1 – Sep 10, 72d) compares againstReads as
Same span, prev periodApr 1 – Jun 11 (Q2's first 72 days) quarter-over-quarter, boundary-anchored
The days just beforeApr 20 – Jun 30 (the 72 days before Jul 1) a rolling "how are we doing lately"
Both are like-for-like on length. Built as shown: aligned is the default, because quarter-over-quarter is the question the bucket control was trying to answer. A custom range has no period boundary, so it always rolls — the status line says when that happens rather than leaving it as a silent difference.
2b. And should B stay put once you set it yourself?
Built as shown: setting B by hand pins it (the chip goes solid) and it stops following A. The ⇄ button toggles that. Alternative: B never moves on its own at all.
3. What should happen when the two ranges are different lengths?
Built as shown: both are drawn from their own day 1, each running its own length, and the status line says the totals are not like-for-like. There is a Match length action on the B chip. Alternative: normalise the x-axis to % of period elapsed, which makes the shapes comparable but the axis abstract.
4. Is auto granularity right?
Built as shown: ≤31 days plots by day, ≤182 by week, longer by month — overridable. This is where Day/Week/Month now lives: how the x-axis is bucketed, not what period is being compared. That separation is what makes arbitrary ranges tractable.
5. What should Trend show, given there are now two ranges?
Built as shown: Trend draws range A over time for the top 6 categories; click a category and it charts A against B for that one alone. Showing both ranges for all categories at once is 12–24 lines, which is unreadable. Alternative: Trend plots the delta per category.
6. Should Table become the default view?
With two explicit ranges, "A total, B total, Δ, Δ%" per category is the most direct answer to the question being asked, and it is the only view that needs no chart at all. Currently Vs is the default. Built as shown: Vs stays default. Easy to flip.
7. Anything to keep from the current controls?
The To date pill becomes unnecessary — "this month so far vs the same days last month" is just what the auto-B rule produces. Built as shown: it is removed. Level (L2/L3), Measure ($/units), store scope and the four views are all unchanged.

Notes on correctness

  • BL12/BL16 still gate. They share a Clover merchant; category-series already applies wrsGateDates, so a range straddling the 2026-06-14 cutover does not double-count. Nothing here changes that.
  • An absent day stays absent. The feed omits days with no snapshot rather than returning zero; a range containing a gap shows a shorter line, not a dip to zero.
  • Part-covered periods stop being a concept. There is no bucket to be partly covered — you asked for these dates, so you get these dates. The class of bug that produced "every category down exactly −24.7%" cannot occur on this path.
