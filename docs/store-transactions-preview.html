Transactions — a fourth tab beside Item Sales

A working click-through of a Transactions tab on the store detail page — the screen a manager reaches from their store card's View Details →. It sits fourth in the existing segmented control, right after Item Sales, and mirrors what Clover shows: the five transaction tabs, the payments list, and the payment detail behind a row. Every control below is live — switch tabs, change store or date, search, and click any row to open its detail.

Yes, this is possible. Clover exposes /v3/merchants/{mId}/payments, and the worker already calls its sibling endpoints for refunds and credits — it has simply never asked for a single payment-level field. The one thing the API will not give back is history older than about 90 days, and that limit is Clover's own. The notes under the panel say exactly which column comes from where.

Nothing is wired up, and no app code has been changed. This is a static prototype in docs/ — a directory scripts/build.sh deliberately excludes, so it never reaches production. The numbers are synthetic (seeded, so they are stable between reloads) — plausible shapes on real store and staff names, not your sales. Read the layout and the behaviour, not the figures.

The five tabs, and what backs each
1 Payments — a new call, but a well-trodden one GET /v3/merchants/{mId}/payments. The worker has never called it — nor /employees, /tenders, /customers, /authorizations (I grepped: zero hits). It does already page /orders with expand=payments, so those payment objects are already arriving and nothing reads a single field off them.
2 Refunds — already implemented fetchRefundElements pages /v3/refunds with expand=payment,orderRef today, for the daily rollup. The Refunds tab is a different rendering of a fetch that already runs.
3 Manual Refunds — already implemented, and named confusingly Clover's UI says "Manual Refunds"; the API calls them credits. fetchManualRefunds already pages /v3/credits. (/v3/manual_refunds does not exist — it answers 405 to a GET.)
4 Voids — a filter, not a fetch A void is a payment whose result is not SUCCESS, or a credit flagged voided. The worker already discards exactly these when totalling a day; the Voids tab shows the rows it throws away.
5 Authorizations — real, but almost always empty here Clover has a Get all authorizations endpoint, so the tab is buildable. But an authorization is a pre-auth — a hold placed on a card to be captured later, the thing hotels and car-rental desks use. A register that rings a sale and takes payment in one step does not create them. Expect this tab to read "none" on almost every store-day; it is included so the screen matches Clover rather than because it will carry traffic. Worth cutting if you would rather not have a tab that is permanently empty.
The one real limit
! About 90 days of history, and that ceiling is Clover's Clover documents the cap on Get all payments in terms: "the results will not exceed 90 days", even when the query asks for a wider span. Nothing per-transaction has ever been stored on our side — D1's daily_sales is one row per store-day, and the KV item snapshot is category-grain — so there is no local copy to fall back on. A Transactions tab is therefore a live, read-only window on roughly the last quarter. Older dates are not slow to load; they are gone.

This is the same retention edge that has cost this repo real data three times, and it is why the panel states the limit on the surface instead of rendering an empty table that a manager would read as "no sales that day".
→ If you want it to outlive 90 days, say so now The fix is to persist each day's payments as they are fetched — a new per-payment table written by the nightly job that already runs. Then the tab reads Clover for today and our own copy for everything older, and the archive deepens from the day it ships. That is a materially bigger change than the read-only version, so it is a decision for you rather than something to assume: read-only first is the smaller, safer step, and it does not foreclose the archive.
Cost, safety, and what it would touch
A Read-only. It writes nothing. No KV write, no D1 write, no Clover mutation — the same posture as sales-diag. None of the destructive-operation rules are in play because nothing is overwritten; there is no backup to take and no history to lose.
B About three to five Clover calls per store-day One payments page (Clover's max is limit=1000; a busy store-day is a few hundred), plus refunds and credits, plus the tender and employee maps — and those two are small, change rarely, and cache like the existing 24-hour category map. Comfortably inside the worker's subrequest budget, and inside Clover's rate limit of 16 requests per second per token.
C Four small edits in the app, one new worker action Frontend: a fourth button and panel in the store-detail segmented control, plus two map entries and a lazy-load branch in switchStoreTab. The day-strip picker already takes a handler-name argument, so the date control comes free. Worker: one new ?action=transactions — store-scoped via canAccessStore, listed in ACTION_BUSINESS (without that entry the business gate 403s every call), and fetched through the retrying Clover helper so a rate-limit answer is never mistaken for an empty day.
D One trap specific to Indy East BL16 and the closed BL12 (Wyoming) share one Clover merchant account. A per-store payments query for BL16 returns Wyoming's rows too unless the existing 2026-06-14 cutover is applied. Every other store maps to its own merchant.
